1. **CI/CD Deploy‑Eligibility Gate** – Guarantees that only builds that satisfy every policy are released, eliminating manual triage.

**State & questions** – JSON output of a CI run (tests, lint, coverage).  
- “Are all test suites marked PASS?”  
- “Is line‑coverage ≥ 80 %?”  
- “Did lint finish with zero errors?”  
- “Is the build artifact size under the declared limit?”  
- “Does the SBOM list no ‘critical’ vulnerabilities?”  

**Ground truth** – A deterministic script parses the CI JSON, extracts each status field, and emits true/false for each question. No human labels needed.

**Hypothesis & metric** – Using the Jev gate reduces the false‑positive rate (releases blocked for non‑issues) by > 30 % compared with the raw CI status check. Metric: false‑positive % on a set of 500 historical runs.

**Lattice features** – TypeSafe Jev (fast, calibrated yes/no); binary deterministic gate (all must GO); caching by run‑ID hash; drift re‑check on any change to the CI JSON.

2. **Terraform Plan Drift Gate** – Stops infrastructure changes that would violate safety policies before apply.

**State & questions** – Terraform plan JSON (resource changes).  
- “Will any resource be destroyed?”  
- “Will any security‑group rule allow unrestricted inbound SSH?”  
- “Will any resource exceed the declared cost ceiling?”  
- “Will any tag be missing on a production resource?”  
- “Will any IAM policy grant */* permission?”  

**Ground truth** – A Go/Python parser reads the plan, extracts resource actions, and compares against a policy table. Produces a boolean per question.

**Hypothesis & metric** – Automated Jev gating catches ≥ 95 % of risky changes that currently slip through manual review. Metric: recall of policy violations in a 30‑day production sample.

**Lattice features** – Jev yes/no checks (≈ 10 ms each); coordinated gate (k = 2 independent safety proofs required); state hash caching; drift detection via plan hash.

3. **Dependency‑Vulnerability Guard** – Prevents shipping code with known high‑severity CVEs.

**State & questions** – `package-lock.json` (or equivalent).  
- “Does any direct dependency have a CVE with CVSS ≥ 7.0?”  
- “Does any transitive dependency ship a vulnerable version of `lodash`?”  
- “Are all dev‑only packages marked as `devDependencies` (no production exposure)?”  
- “Does the lockfile contain a package from a disallowed registry?”  
- “Is the lockfile newer than the last audit timestamp?”  

**Ground truth** – A script runs `npm audit --json` (or equivalent) and maps each vulnerability to the lockfile entries, returning true/false per question.

**Hypothesis & metric** – The guard cuts the number of CVE‑related incidents in production by ≥ 40 %. Metric: incidents per quarter before/after deployment.

**Lattice features** – TypeSafe Jev (fast, batched checks); binary gate (any CVE triggers REFUTED); caching by lockfile hash; periodic drift re‑verification (alert on new audit data).

**Ground truth** – A script fetches the merged PR list via GitHub API, extracts their numbers, and performs a regex search in the changelog. Returns true/false per PR.

**Hypothesis & metric** – Automated checking raises changelog recall from ~ 70 % to ≥ 95 % with zero manual effort. Metric: recall % measured on a sample of 200 PRs.

**Lattice features** – Jev calibrated yes/no (fast scanning of long docs); coordinated gate (≥ 90 % of PRs must be present); caching by commit‑range hash; drift detection on new commits.

**Hypothesis & metric** – Jev triage raises routing accuracy from ~ 75 % (human) to ≥ 90 % with lower latency. Metric: % of tickets correctly routed within 1 minute.

**Lattice features** – TypeSafe Jev (fast, many questions per ticket); binary gate (any “yes” on the matching team’s questions triggers GO); caching by ticket‑ID hash; drift re‑check when ticket content is edited.
